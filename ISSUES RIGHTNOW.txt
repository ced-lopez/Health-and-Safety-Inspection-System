Issue 1: Inspection request form field mapping is broken

The RequestInspectionPage.jsx sends form fields with keys that do not match the backend's StoreInspectionRequest validation:

Frontend sends	Backend expects
category (e.g., food_establishment)	inspection_category_id (integer, FK to inspection_categories.id)
application_type (e.g., new)	application_type_id (integer, FK to application_types.id)
business_address	applicant_address
purpose	remarks
The frontend categories (food_establishment, piggery, poultry, dog_raising) also don't match the seeded category slugs (business_establishments, pigery, poultry, animal_raising_dogs). The createInspectionRequest service sends a FormData object, but the backend expects a JSON body with specific fields.

Impact: The "Request Inspection" form will fail server-side validation and return a 422 error.

Issue 2: Resident Dashboard data shape mismatch

ResidentDashboardPage.jsx reads:

data?.stats?.active_clearance — not returned by DashboardController (which returns stats.active_establishments, stats.open_violations, stats.scheduled_inspections, stats.completed_inspectments)
data?.recent_activities — not returned by DashboardController (which returns data.recent_inspections)
Impact: The resident dashboard will show zeros and "No recent activity."

Issue 3: MyApplicationsPage data shape mismatch

MyApplicationsPage.jsx reads req.category and req.application_type as strings, but the API's InspectionRequestResource returns inspection_category (object) and application_type (object). It also reads req.business_address and req.notes/req.purpose but the resource returns applicant_address and remarks.

Impact: Resident application tracking page will display "N/A" for category and application type.

6.2 Documentation vs Implementation Discrepancies
Issue 4: Refactoring plan claims 5 roles, only 4 exist

docs/refactoring-plan.md Section 3.5 states: "User/Role Management — Complete — 5 roles (administrator, barangay_staff, inspector, staff, resident)". The actual RoleSeeder only seeds 4 roles — there is no staff role.

Issue 5: Refactoring plan claims register assigns staff by default

docs/refactoring-plan.md Section 3.4 states: "Auth (register/login/logout/me) — Complete — assigns staff by default". The actual AuthController::register() assigns the resident role.

Issue 6: Phase 1 doc references Laravel 12, project runs Laravel 13

docs/phase-1-project-planning-and-architecture.md Section 15 states: "The project brief requests Laravel 12, but backend/composer.json currently requires laravel/framework version ^13.8". The refactoring plan (Section 3.1.5) confirms the decision to upgrade to Laravel 13. The Phase 1 doc is stale.

6.3 Architecture Concerns
Issue 7: inspection_schedules table is legacy but still actively used

The Phase 1 doc (Section 15) and database design doc both note that inspection_schedules is "existing table retained for backward compatibility" and "should be renamed or migrated to assignment-based terminology." However, it remains the primary mechanism for compliance checklists and inspection reports via InspectionSyncService::sync(). The new inspection_assignments table (for inspector mobile sync) is separate and does not link to inspections directly.

This creates a dual-path architecture: schedules → inspections (for compliance checklists/reports) vs. assignments (for mobile sync). The Phase 7 flow (#9-11) describes the inspector using "dynamic checklists" but the actual ComplianceChecklistController operates on InspectionSchedule, not InspectionAssignment.

Issue 8: No mobile/ directory exists

The updated prompt (Section 1) and all phase docs consistently call for a Flutter mobile application, but no mobile/ directory exists in the project.

Issue 9: Frontend .env.example is minimal

The frontend .env.example only contains VITE_API_URL=http://localhost:8000/api. Missing: VITE_APP_NAME, other environment hints.

Issue 10: resources/js/app.js is a stub

The file backend/resources/js/app.js contains only a comment (//). This is the Vite entry for backend Blade views but appears unused since the backend is a pure API and the PDF template uses inline styles.
